# SKILL: REQUIREMENT-REVIEW

## PURPOSE

Проанализировать актуальные требования и подготовить структурированный Requirement Review Artifact.

Результат должен содержать:

- классификацию требований;
- выявленные GAP, AMB и CONF;
- traceability к исходным требованиям.

## INPUTS

Используй только переданный контекст:

- актуальные требования;
- бизнес-правила, если указаны;
- критерии приёмки, если указаны;
- непосредственно связанные материалы.

Не используй:

- требования других функциональностей;
- устаревшие версии;
- предыдущие выводы агента вместо исходных требований.

Не ищи самостоятельно отсутствующую информацию вне переданного контекста.

## CLASSIFICATION

Используй следующие категории:

- **FR** — что система должна делать.
- **BR** — бизнес-правило или ограничение предметной области.
- **AC** — проверяемое условие корректности реализации.
- **Constraint** — явно заданное техническое, правовое, security или иное ограничение.
- **Dependency** — фактическая зависимость от другой функциональности, требования или внешней системы.
- **Role** — явно указанный участник взаимодействия.

Не создавай FR, BR или AC, которых нет в исходных требованиях.

## FINDINGS

Фиксируй:

- **AMB** — требование допускает несколько трактовок.
- **GAP** — необходимая информация отсутствует.
- **CONF** — требования содержат взаимоисключающие утверждения.

Не выбирай самостоятельно трактовку AMB или CONF.

Если для однозначного понимания требования недостаточно информации — фиксируй GAP.

Если существуют несколько возможных трактовок — фиксируй AMB.

Если требования содержат взаимоисключающие утверждения — фиксируй CONF.

## PROCEDURE

- определить анализируемую функциональность;
- выделить FR, BR, AC и Constraints;
- определить Dependencies и Roles при наличии;
- выявить AMB, GAP и CONF;
- проверить полноту traceability;
- проверить отсутствие неподтверждённых предположений;
- сформировать результат по `OUTPUT`.

## RULES

- Используй только переданные требования.
- Не изменяй исходный текст.
- Не выдумывай требования, источники, ID, версии, ссылки, данные или поведение системы.
- Если необходимая информация отсутствует — зафиксируй GAP.
- Роли и зависимости фиксируй только при наличии подтверждения в требованиях.
- Исторические версии не используй как активный источник.
- Не используй предыдущий Artifact как источник требований.
- Не создавай Jira-задачи.
- Не создавай Qase-тесты.
- Не выполняй действия вне анализа требований.
- Не выбирай трактовку неоднозначного требования самостоятельно.
- Не устраняй противоречия самостоятельно.
- Не превращай предположение в требование.

## OUTPUT

Результат должен содержать:

### Functional Requirements

- ID
- Функциональность
- Описание
- Источник

### Business Rules

- ID
- Правило
- Requirement ID
- Источник

### Constraints

- ID
- Ограничение
- Тип
- Источник

### Acceptance Criteria

- ID
- Критерий
- Requirement ID
- Источник

### Dependencies

- ID
- Зависимость
- Тип
- Requirement ID
- Источник

### Roles

- ID
- Роль
- Функциональность
- Описание взаимодействия
- Источник

### AMB

- ID
- Описание
- Источник
- Критичность
- Требуемое уточнение

### GAP

- ID
- Что отсутствует
- Для чего необходимо
- Критичность

### CONF

- ID
- Суть противоречия
- Где конфликтует
- Критичность
- Источник

Результат должен быть пригоден для Jira/Qase без повторного анализа требований.

## TRACEABILITY

Каждый FR, BR, Constraint и AC должен иметь связь с исходным требованием, если источник доступен.

Для Dependency и Role источник указывается при наличии.

Если источник или ID отсутствует:

- не выдумывать значение;
- явно указать отсутствие;
- зафиксировать GAP, если это препятствует однозначному пониманию или проверке.

Traceability не должна создаваться на основании предположений.

Каждая запись должна быть связана только с тем требованием, которое фактически подтверждает её содержание.

## COMPLETION CRITERIA

Skill считается выполненным, если:

- все доступные требования классифицированы;
- FR / BR / AC / Constraints выделены;
- Dependencies и Roles определены при наличии;
- AMB / GAP / CONF зафиксированы;
- traceability сформирована;
- неподтверждённые предположения отсутствуют;
- результат соответствует структуре `OUTPUT`;
- результат пригоден для последующих Jira/Qase этапов без повторного анализа требований.
