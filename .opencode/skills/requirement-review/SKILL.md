## SKILL: REQUIREMENT-REVIEW

## PURPOSE
Выполнить анализ требований перед их использованием для формирования задач разработки и тестирования и проектирования тестовой модели. Skill предназначен для выявления содержания требований, определения структуры, неоднозначностей, противоречий и отсутствующей информации.

## INPUTS
Для применения Skill необходимы:
- актуальные требования текущей функциональности
- связанные с требованиями бизнес-правила
- критерии приёмки
- дополнительные материалы только если они непосредственно относятся к анализируемому функционалу

Не используй:
- требования других функциональностей
- устаревшие версии требований
- предыдущие выводы агента вместо исходных требований

Skill не должен самостоятельно искать недостающие входные данные вне пределов переданного контекста.

## GLOSSARY (ГЛОССАРИЙ)
Для единообразной классификации применяй определения:

Функциональное требование - описание того, что система должна делать (поведение, доступное пользователю/системе).

Бизнес-правило - политика или ограничение предметной области, которому должно следовать поведение системы.

Критерий приёмки - условие, при котором функциональность считается реализованной корректно (проверяемое утверждение).

Ограничение - рамка реализации (техническая, правовая, производительности, безопасности), заданная в требованиях.

Зависимость - связь с другой функциональностью/требованием, влияющая на порядок реализации или тестирования.

Роль - участник/актор (пользователь, система, внешний сервис), взаимодействующий с функциональностью; определяется из требований.

Неоднозначность - формулировка требования, допускающая более одного толкования; фиксируется для уточнения у владельца продукта.

Противоречие - взаимоисключающие утверждения в требованиях; фиксируется для эскалации и снятия конфликта.

## PROCEDURE
При анализе требований необходимо:
1. определить функциональность, которую необходимо проанализировать
2. выделить бизнес-правила
3. определить критерии приёмки
4. определить ограничения
5. выявить зависимости
6. выявить роли
7. выявить неоднозначности
8. определить отсутствующую информацию
9. выявить противоречия
10. сформировать структурированный результат анализа по шаблону Output

## RULES
При выполнении анализа необходимо соблюдать следующие правила:
- не добавлять отсутствующие требования
- отсутствующая информация не должна выдаваться за подтверждённое требование
- не изменять исходный текст
- в рамках этого скилла не создавать задачи в Jira
- в рамках этого скилла не создавать тестовую модель в Qase
- не выполнять действия, которые не имеют отношения к анализу требований
- Skill только фиксирует и классифицирует проблемы; решение и эскалация - зона агента

## OUTPUT
Результат Skill должен содержать и быть оформлен по следующему шаблону.

1. Список функциональных требований: ID, Функциональность, Описание, Источник (ключ/якорь исходного требования для прослеживаемости).

2. Бизнес-правила: ID, Правило, Относится к требованию, Источник.

3. Ограничения: ID, Ограничение, Тип, Источник.

4. Критерии приёмки: ID, Критерий, Относится к требованию.

5. Зависимости: ID, Зависимость, Тип (до/после/внешняя).

6. Роли: ID, Роль, Функциональность, Описание взаимодействия.

7. Найденные неоднозначности: ID, Описание, Источник, Критичность, Предлагаемое уточнение.

8. Отсутствующая информация: ID, Что отсутствует, Для чего необходимо, Критичность.

9. Найденные противоречия: ID, Суть противоречия, Где конфликтует, Критичность.

Результат должен быть структурирован, чтобы следующий этап (Jira/Qase) мог использовать его без повторного анализа требований.

## EXAMPLES (ЭТАЛОННЫЙ ПРИМЕР)
Пример заполнения результата анализа:

1. Функциональное требование:
   FR-1 | Авторизация пользователя | Система должна позволять зарегистрированному пользователю входить по email и паролю | Confluence: REQ-42 (якорь #auth)

2. Бизнес-правило:
   BR-1 | Пароль должен содержать не менее 8 символов | Относится к FR-1 | REQ-42

4. Критерий приёмки:
   AC-1 | При корректных email и пароле пользователь перенаправляется на главную страницу | Относится к FR-1

7. Неоднозначность:
   AMB-1 | Не указано, блокируется ли аккаунт после N неудачных попыток | REQ-42 | Высокая | Уточнить политику блокировки у владельца продукта

## COMPLETION CRITERIA
Skill считается успешно применённым, если:
- переданные требования проанализированы
- выделены функциональные требования, бизнес-правила, критерии приёмки, ограничения
- зафиксированы зависимости и роли (при наличии)
- обнаруженные неоднозначности, противоречия и недостаток информации зафиксированы
- результат оформлен по шаблону Output и пригоден для использования без повторного анализа
