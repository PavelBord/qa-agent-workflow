# SKILL: REQUIREMENT-REVIEW

## PURPOSE

Проанализировать актуальные требования и подготовить структурированный Requirement Review Artifact.

Результат должен содержать:

- классификацию требований;
- выявленные GAP, AMB и CONF;
- traceability к исходным требованиям.

## INPUTS

Используй только переданный контекст:

- актуальные требования;
- бизнес-правила, если указаны;
- критерии приёмки, если указаны;
- непосредственно связанные материалы.

Не используй:

- требования других функциональностей;
- устаревшие версии;
- предыдущие выводы агента вместо исходных требований.

Не ищи самостоятельно отсутствующую информацию вне переданного контекста.

## CLASSIFICATION

Используй следующие категории:

- **FR** — что система должна делать.
- **BR** — бизнес-правило или ограничение предметной области.
- **AC** — проверяемое условие корректности реализации.
- **Constraint** — явно заданное техническое, правовое, security или иное ограничение.
- **Dependency** — фактическая зависимость от другой функциональности, требования или внешней системы.
- **Role** — явно указанный участник взаимодействия.

Не создавай FR, BR или AC, которых нет в исходных требованиях.

## FINDINGS

Фиксируй:

- **AMB** — требование допускает несколько трактовок.
- **GAP** — необходимая информация отсутствует.
- **CONF** — требования содержат взаимоисключающие утверждения.

Не выбирай самостоятельно трактовку AMB или CONF.

Если для однозначного понимания требования недостаточно информации — фиксируй GAP.

Если существуют несколько возможных трактовок — фиксируй AMB.

Если требования содержат взаимоисключающие утверждения — фиксируй CONF.

Для каждого AMB / GAP / CONF укажи затронутые Requirement ID, блокирует ли находка продолжение, причину и требуемое уточнение. Блокировку определяй по влиянию на реализацию и проверку согласно Gate #1 в AGENTS.md, а не только по критичности. Не выбирай неподтверждённую трактовку, чтобы получить PASS.

## PROCEDURE

- определить анализируемую функциональность;
- выделить FR, BR, AC и Constraints;
- определить Dependencies и Roles при наличии;
- выявить AMB, GAP и CONF;
- проверить полноту traceability;
- для каждого обязательного FR проверить наличие подтверждённых AC, достаточных для задачи его реализации; отсутствие таких AC фиксировать как блокирующий GAP, не дописывать критерии самостоятельно;
- проверить отсутствие неподтверждённых предположений;
- сформировать результат по `OUTPUT`.

## RULES

- Используй только переданные требования.
- Не изменяй исходный текст.
- Не выдумывай требования, источники, внешние ID, версии, ссылки, данные или поведение системы.
- Если необходимая информация отсутствует — зафиксируй GAP.
- Роли и зависимости фиксируй только при наличии подтверждения в требованиях.
- Исторические версии не используй как активный источник.
- Не используй предыдущий Artifact как источник требований.
- Не создавай Jira-задачи.
- Не создавай Qase-тесты.
- Не выполняй действия вне анализа требований.
- Не выбирай трактовку неоднозначного требования самостоятельно.
- Не устраняй противоречия самостоятельно.
- Не превращай предположение в требование.

## OUTPUT

Результат должен содержать:

### Готовность

- Анализ завершён: да / нет.
- Требования готовы к следующим этапам: да / нет.
- Блокирующие находки: ID и причины либо явно «отсутствуют».
- Requirement Review: PASS / FAIL / BLOCKED — оценка этапа reviewer, не решение Gate #1. PASS возможен только при завершённом анализе, готовности и отсутствии блокирующих находок; BLOCKED означает необходимость обязательных данных или уточнений, FAIL — иной дефект, препятствующий продолжению. Решение Gate #1 записывает только оркестратор.
- Обеспеченность обязательных FR критериями: FR → подтверждённые AC → основание достаточности либо блокирующий GAP.

### Functional Requirements

- ID
- Функциональность
- Описание
- Источник

### Business Rules

- ID
- Правило
- Requirement ID
- Источник

### Constraints

- ID
- Ограничение
- Тип
- Источник

### Acceptance Criteria

- ID
- Критерий
- Requirement ID
- Источник

### Dependencies

- ID
- Зависимость
- Тип
- Requirement ID
- Источник

### Roles

- ID
- Роль
- Функциональность
- Описание взаимодействия
- Источник

### AMB

- ID
- Описание
- Источник
- Критичность
- Требуемое уточнение

### GAP

- ID
- Что отсутствует
- Для чего необходимо
- Критичность

### CONF

- ID
- Суть противоречия
- Где конфликтует
- Критичность
- Источник

При PASS результат должен быть пригоден для Jira/Qase без повторного анализа требований. При блокировке передай оркестратору необходимые уточнения; следующий этап не запускается.

## TRACEABILITY

Для классификации и находок назначай стабильные локальные ID (FR-1, AC-1, AMB-1 и т. п.), явно обозначая их как локальные. Это идентификаторы записей анализа, а не вымышленные внешние Requirement ID. Сохраняй связь с подтверждённым источником и конкретным фрагментом текста; при resume сохраняй ID неизменённых записей и не переиспользуй ID для другого содержания. Если внешний Requirement ID отсутствует, локальный ID вместе с идентичностью источника служит mapping последующих этапов; отсутствие внешнего ID явно зафиксируй.

Каждый FR, BR, Constraint и AC должен иметь связь с исходным требованием, если источник доступен.

Для Dependency и Role источник указывается при наличии.

Если источник или внешний ID отсутствует:

- не выдумывать значение;
- явно указать отсутствие;
- зафиксировать GAP, если это препятствует однозначному пониманию или проверке.

Traceability не должна создаваться на основании предположений.

Каждая запись должна быть связана только с тем требованием, которое фактически подтверждает её содержание.

## COMPLETION CRITERIA

Skill считается выполненным, если:

- все доступные требования классифицированы;
- FR / BR / AC / Constraints выделены;
- Dependencies и Roles определены при наличии;
- AMB / GAP / CONF зафиксированы;
- traceability сформирована;
- неподтверждённые предположения отсутствуют;
- результат соответствует структуре `OUTPUT`;
- готовность к следующим этапам оценена отдельно; завершение анализа при наличии блокирующих находок не даёт PASS.

## EXAMPLE

```text
FR-1 | Авторизация пользователя | Вход по email и паролю | REQ-42
BR-1 | Пароль обязателен | FR-1 | REQ-42
AC-1 | Валидные данные → успешная авторизация | FR-1 | REQ-42
AMB-1 | Не определено поведение после N неудачных попыток | REQ-42 | High | Уточнить
GAP-1 | Не указано значение N | Для определения политики блокировки | High
```

Пример условный: политику блокировки и значение N анализировать только при наличии основания в переданных требованиях.
