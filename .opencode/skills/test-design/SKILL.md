# SKILL: QASE TEST MODEL DESIGN

## PURPOSE

Создать тестовую модель Qase с полной traceability:

`Requirement → Jira Task → Qase Test Case`

## INPUT

Обязательные условия:

- текущие `artifacts/requirement-review.md` и `artifacts/jira-tasks.md` со статусами этапов PASS
- Gate #1 и Gate #2 = PASS, подтверждённые оркестратором для актуальных входов
- подтверждённый Qase project и существующая target suite в нём

`Requirement ID` извлекается из `artifacts/requirement-review.md`.

Для каждого теста обязателен Jira Task ID подтверждённой задачи соответствующего scope из текущего Jira-артефакта.

Источник требований — только `Requirement Review Artifact`.

Источник Jira mapping — только `artifacts/jira-tasks.md`.

Не использовать:

- предположения;
- неподтверждённые данные;
- исторические версии;
- самостоятельно найденные требования.

## PROCEDURE

### Test Design

Для каждой функциональности определить необходимые тесты на основании Requirement Review:

- positive;
- negative — только для явно заданного поведения при ошибке или правил валидации;
- boundary — только для заданных ограничений;
- business rules / AC.

Не создавать тесты, основанные только на общих QA-предположениях.

Для каждого теста определить:

- Suite;
- заголовок;
- описание;
- предусловия, если определены;
- классы тестовых данных или ссылку на управляемые данные, когда они нужны, без секретов;
- шаги;
- ожидаемый результат;
- Requirement ID;
- FR/BR/AC mapping;
- Jira Task ID подтверждённой задачи соответствующего scope.

Если нельзя определить необходимые данные, подготовку состояния или наблюдаемый результат, зафиксируй BLOCKED и передай вопрос оркестратору. Не конкретизируй неоднозначность из Requirement Review самостоятельно и не создавай такой кейс как готовый.

### Qase Validation

До внешнего создания проверь проект тестов по правилам ниже. Запиши обоснование в текущем разделе существующего `artifacts/qase-test-model.md`; для ещё не созданных тестов явно укажи «проект, Qase ID отсутствует». Не выдавай локальный проект за созданный кейс.

### Проверка достаточности тестов

- Для составного правила перечисли отдельно проверяемые условия, сохраняя исходный Requirement ID. Это разбор существующего требования, а не создание новых FR / BR / AC.
- Для каждого независимого условия запрета подбери сценарий, где нарушено только оно, а остальные условия выполнены. Сценарий с несколькими нарушениями не заменяет независимые проверки: отказ может быть вызван другим нарушением. Если изоляция невозможна из-за зависимости условий, зафиксируй причину и обоснованный способ проверки.
- Для явно заданной числовой границы проверь ближайшее допустимое и недопустимое значение с учётом типа данных. Не придумывай отсутствующие границы. Добавь допустимый сценарий, чтобы модель обнаруживала реализацию, отклоняющую любые данные.
- Для каждого условия ответь: «Если реализация перестанет проверять только это условие, какой сценарий покажет ошибку?» Если такого сценария нет, покрытие условия неполное. Это содержательный разбор модели, не заявление о выполненном mutation testing.
- Параметризованный кейс допустим, если варианты данных, подготовка и ожидаемый результат заданы для каждого варианта. Отдельный Qase-кейс для каждой строки необязателен.

### Данные и повторяемость

Для тестов, меняющих состояние, укажи исходное состояние, способ его подготовки и повторного запуска. Например, сценарий создания требует заранее свободного идентификатора; сценарий дубликата — заранее существующего. Два успешных сценария не должны расходовать один и тот же идентификатор без восстановления состояния.

Каждый вариант параметризованного теста начинает работу с определённого состояния: фраза «повторить для другого поля» не должна оставлять неявно пустыми предыдущие поля. Подготовка данных не означает разрешение удалять пользователей или менять настройки: использовать только согласованный механизм, реальные секреты не сохранять.

### Наблюдаемый результат

Укажи, по какому доступному признаку тестировщик отличит успех от ошибки. «Пользователь создан» без способа проверки недостаточно. Для отсутствия побочного эффекта нужен доступный способ наблюдения и, для асинхронного поведения, обоснованный период проверки. Отсутствие письма во входящих само по себе не доказывает отсутствие отправки.

Не выдумывай доступ к БД, API, журналам или почтовому сервису, а также сроки ожидания. Если необходимый способ проверки или подготовки не подтверждён, зафиксируй BLOCKED и уточнение через оркестратора.

### Проверка Qase

Перед созданием:

- подтвердить существование заданной target suite по ID и принадлежность целевому проекту;
- проверить существующие test cases;
- выполнить duplicate check;
- определить отсутствующие тесты.

Не создавать дубликаты.

Если Qase project или target suite недоступны:

- `BLOCKED`;
- тесты не создавать.

### Test Creation

Создавать только отсутствующие тесты в подтверждённой существующей target suite. Создание suites выполняется отдельной задачей вне workflow. При использовании upsert выполнять только создание без ID существующего кейса; если режим создания нельзя гарантировать — BLOCKED.

После создания каждого теста:

- выполнить Qase GET verification;
- проверить Qase Test Case ID;
- проверить заголовок;
- проверить Requirement ID;
- проверить FR/BR/AC mapping;
- сравнить проект, suite, описание, предусловия, данные, все шаги и ожидаемые результаты с подготовленным тестом;
- проверить соответствие Requirement Review.

Те же поля проверяй у используемых существующих кейсов, включая отсутствие необязательных значений. Сохраняй время GET, ID, сравнённые поля и расхождения. При неопределённом результате создания следуй FAILURE BEHAVIOUR в AGENTS.md.

Тест считать `created` только после успешной GET verification.

Существующие подтверждённые тесты не изменять.

Тесты для `BLOCKED` Jira-задач не создавать.

Если создание теста завершилось ошибкой:

- не считать тест созданным;
- установить статус `error`;
- зафиксировать причину.

Если GET verification завершилась ошибкой:

- установить статус `error`;
- не считать тест подтверждённым.

### Jira Mapping

Для каждого теста определить Jira Task ID из `artifacts/jira-tasks.md`.

Обязательная связь: `Requirement ID → Jira Task ID → Qase Test Case ID`.

Jira-задача должна быть подтверждена через GET в текущем Jira-артефакте и соответствовать проверяемому scope. При отсутствии такой задачи — BLOCKED: тест не создавать, mapping не придумывать, передать вопрос оркестратору. N/A для Jira mapping недопустим.

## DUPLICATE CHECK

Применяй контекст и полноту поиска по RESUME в AGENTS.md: источник требований, целевой проект и все страницы результатов. Сохрани запросы, охват и найденные ID в текущем разделе артефакта.

Проверять существующие тесты по:

- Requirement ID;
- FR;
- BR;
- AC;
- функциональности;
- заголовку.

Сравнивай также предусловия, класс данных, действие и ожидаемый результат. Несколько разных сценариев для одного Requirement ID допустимы; одинаковый заголовок или mapping сами по себе не доказывают дубликат. Неоднозначное совпадение — BLOCKED. Несоответствие найденного кейса новой версии требований требует эскалации через оркестратора, а не создания его копии.

При обнаружении существующего теста:

- не создавать дубликат;
- сохранить его Qase Test Case ID;
- выполнить необходимую GET verification;
- зафиксировать статус `existing`.

Если duplicate check невозможно выполнить:

- установить `BLOCKED`;
- тест не создавать;
- зафиксировать причину.

## COVERAGE

Рассчитать покрытие:

- FR;
- BR;
- AC.

Для каждого определить:

`total / covered / uncovered / coverage %`

Покрытие считается только по тестам со статусом:

- `created` — после успешной GET verification;
- `existing` — после подтверждения существующего теста.

Тесты со статусом `blocked` или `error` не учитываются как покрытие.

Mapping учитывается как покрытие только если тест проверяет требование, воспроизводим и имеет наблюдаемый результат. Наличие кейса с нужным ID недостаточно. Покрытие моделью не означает выполнение тестов; без свидетельств запуска не заявляй успешное выполнение.

В текущем разделе артефакта сохрани таблицу: `Requirement ID → условие / граница → сценарий / вариант данных → способ проверки → полное / частичное / BLOCKED покрытие`. Требование с непроверенным обязательным условием считается частично покрытым и не входит в covered при расчёте 100%. Частичные требования перечисляй среди непокрытых с указанием недостающих проверок.

Успешный GET подтверждает сохранение кейса, но не достаточность его дизайна. При обнаружении недостатка существующего кейса сохрани исторический факт создания, отдельно отметь текущий дефект дизайна и пересчитай покрытие; не изменяй внешний кейс и не создавай заменяющую копию в этом workflow. Передай исправление оркестратору для отдельной явно разрешённой задачи.

Правила:

- если `total > 0` → coverage должен быть `100%`;
- если `total = 0` → coverage = `N/A`;
- непокрытые требования должны быть явно перечислены.

Для успешного завершения:

- FR = `100%` или `N/A`;
- BR = `100%` или `N/A`;
- AC = `100%` или `N/A`.

Не создавать искусственные тесты для требований, которых нет.

## OUTPUT

Сохранить результат в:

`artifacts/qase-test-model.md`

Для каждого теста сохранять:

- Qase Test Case ID;
- Suite;
- заголовок;
- тип;
- предусловия и необходимые данные или ссылки на них без секретов;
- подготовку состояния и порядок повторного запуска, если тест меняет данные;
- способ наблюдения ожидаемого результата;
- шаги;
- ожидаемый результат;
- Requirement ID;
- FR/BR/AC mapping;
- Jira Task ID;
- статус:
  - `created`
  - `existing`
  - `blocked`
  - `error`.

Также сохранить:

- FR coverage;
- BR coverage;
- AC coverage;
- непокрытые требования;
- результаты duplicate check;
- результаты GET verification;
- ошибки;
- блокировки;
- эскалации;
- `Requirement → Jira Task → Qase Test Case`.

Также сохрани таблицу покрытия условий и результаты проверки достаточности, данных и наблюдаемости. Отсутствующий механизм подготовки или наблюдения явно отмечай, не заполняй предположением.

Artifact должен содержать:

`Qase Stage: PASS / FAIL / BLOCKED`

## RULES

- Не выдумывать требования.
- Не выдумывать сценарии, которые не следуют из требований.
- Не выдумывать ожидаемые результаты.
- Каждый тест должен иметь requirement mapping.
- Не создавать suites и дубликаты тестов.
- Не изменять существующие тесты.
- Не изменять Test Runs и результаты.
- Не изменять настройки Qase.
- Не анализировать требования повторно.
- Не создавать Jira-задачи.
- Не считать тест созданным без успешной Qase GET verification.
- Ошибку авторизации считать блокирующей.
- Не логировать секреты, токены и пароли.
- Не считать `PASS`, если существуют нерешённые обязательные `BLOCKED` или `ERROR`.
- Не использовать Qase Test Case как источник требований.
- Не использовать Jira как источник требований.
- Не считать `blocked` или `error` тесты покрывающими требования.

## COMPLETION CRITERIA

Skill выполнен успешно, если:

- Requirement Review и Jira Stage = `PASS`, Gate #1 и Gate #2 подтверждены оркестратором для актуальных входов;
- каждый созданный или существующий тест имеет Requirement ID;
- каждый тест имеет соответствующий FR/BR/AC mapping;
- каждый тест имеет Jira mapping к подтверждённой задаче соответствующего scope;
- дубликаты не созданы;
- каждый новый тест подтверждён через Qase GET;
- существующие тесты подтверждены;
- FR coverage = `100%` или `N/A`;
- BR coverage = `100%` или `N/A`;
- AC coverage = `100%` или `N/A`;
- отсутствуют непокрытые обязательные требования;
- отсутствуют нерешённые обязательные `BLOCKED` / `ERROR`;
- сохранена связь `Requirement → Jira Task → Qase Test Case`;
- результат сохранён в `artifacts/qase-test-model.md`.
