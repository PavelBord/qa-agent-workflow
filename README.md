# qa-agent-workflow — QA Workflow

Проект для подготовки QA-артефактов с помощью агентов OpenCode: ревью требований, формирование задач Jira и проектирование тестовой модели Qase.

Основной агент `qa-orchestrator` передаёт этапы специализированным сабагентам и проверяет Quality Gates. Правила процесса определены в [AGENTS.md](AGENTS.md).

> Статус: прототип для пилотного использования с контролем QA. Переходы описаны инструкциями и проверяются локальным валидатором состояния. Валидатор проверяет структуру и согласованность записей; содержательную оценку Gates выполняет оркестратор. Самостоятельного runtime-перехвата внешних вызовов нет. Полный интеграционный запуск в рамках последнего локального аудита не выполнялся.

## Процесс

```text
Подтверждённые требования
    → requirements-reviewer
    → Quality Gate #1
    → jira-task-creator
    → Quality Gate #2
    → qase-test-model-designer
    → Quality Gate #3
```

Следующий этап запускается только после `PASS` предыдущего Gate. При `FAIL` или `BLOCKED` продолжение останавливается, причина фиксируется в артефакте и передаётся пользователю для разрешения с владельцем продукта / Lead QA.

| Этап | Результат | Что проверяется |
|---|---|---|
| Requirement Review | Классификация FR / BR / AC / Constraints, неоднозначности, пробелы, противоречия, traceability | Источник, готовность требований, отсутствие блокирующих находок и неподтверждённых предположений |
| Jira | Созданные или используемые существующие задачи с mapping | Полнота поиска дубликатов, реализация обязательных FR, содержание задач через GET |
| Qase | Тестовая модель с Requirement → Jira → Qase mapping | GET, достаточность сценариев, данные, повторяемость, наблюдаемые результаты и полнота покрытия |

FR — функциональные требования; BR — бизнес-правила; AC — критерии приёмки; Constraints — явно заданные ограничения.

Покрытие тестовой моделью не означает выполнение тестов или успешность продукта. GET подтверждает сохранённое содержание сущности, но не заменяет содержательное ревью.

## Структура

```text
AGENTS.md                              Глобальные правила QA workflow
.opencode/
  agent/
    qa-orchestrator.md                 Основной агент
    requirements-reviewer.md           Ревью требований
    jira-task-creator.md                Задачи Jira
    qase-test-model-designer.md         Тестовая модель Qase
  skills/
    requirement-review/SKILL.md         Методика анализа требований
    task-design/SKILL.md                Методика проектирования задач
    test-design/SKILL.md                Методика проектирования тестов
  tools/
    confluence.ts                      Чтение текущей страницы Confluence
    validate-workflow.mjs               Проверка состояния и регрессионные проверки
artifacts/
  requirement-review.md                Версии ревью требований
  jira-tasks.md                        Задачи, mapping, поиск и GET
```

Схема показывает предусмотренные workflow артефакты. Файлы Jira и Qase создаются на соответствующих этапах. В репозитории уже есть исторические результаты; текущий локальный аудит не запускал эти этапы заново.

## Подготовка окружения

1. Подготовьте OpenCode с настроенным провайдером модели. Откройте проект из его корневой директории.
2. Убедитесь, что доступны основной агент и три сабагента, а также skills из `.opencode/skills/`.
3. Для чтения Confluence обеспечьте доступность зависимости `@opencode-ai/plugin`, импортируемой инструментом. `package.json` отслеживается в Git и содержит команды проверки; зависимости после клонирования установите через `npm --prefix .opencode install`. Валидатор использует только встроенные модули Node.js и не требует установки зависимостей.
4. Подключите Jira и Qase в используемом окружении OpenCode. Конфигурации подключения и credentials этих сервисов в отслеживаемых файлах проекта нет. Включённые имена tools в агентах сами по себе не создают соединение.
5. Сверьте фактически доступные инструменты с именами в файлах соответствующих агентов. Для пилота используйте тестовые проекты и доступную целевую suite Qase.

### Confluence

Инструмент `.opencode/tools/confluence.ts` читает переменные окружения процесса:

| Переменная | Значение |
|---|---|
| `CONFLUENCE_URL` | HTTPS-адрес сайта, например `https://your-site.atlassian.net`, либо адрес с `/wiki` |
| `CONFLUENCE_EMAIL` | Email учётной записи для Basic authentication |
| `CONFLUENCE_TOKEN` | Токен доступа |

Передайте значения процессу OpenCode через ваше окружение. Сам инструмент не загружает `.env`. Не сохраняйте реальные значения в README, артефактах или Git.

`pageId` должен быть положительным целым числом. Инструмент запрашивает `/wiki/api/v2/pages/{pageId}?body-format=storage`, проверяет ID, статус `current`, заголовок, номер версии и непустое содержимое. Таймаут чтения — 15 секунд; перенаправления запрещены.

Инструмент маркирует ошибки как `RETRYABLE` или `NON_RETRYABLE`, но сам не повторяет запросы. Повторы координируются по правилам `AGENTS.md`.

### Jira и Qase

- Jira: нужны чтение контекста проекта и метаданных типов задач, поиск JQL, создание задачи и GET. Точные ожидаемые имена указаны в [jira-task-creator.md](.opencode/agent/jira-task-creator.md).
- Qase: нужны чтение контекста проекта/suite, полный поиск кейсов, создание и GET. Ожидаемые имена указаны в [qase-test-model-designer.md](.opencode/agent/qase-test-model-designer.md).
- Создание выполняется только после полного поиска и проверки совпадений. Существующие задачи и тесты не изменяются без отдельного разрешения.

## Первый запуск

Подготовьте актуальный текст требований либо страницу Confluence, однозначную идентичность источника, scope, целевой Jira project, Qase project и suite. Передайте подтверждённые тип и приоритет Jira-задач. Target suite должна уже существовать; создание suites не входит в этот workflow. Уточнения требований должны быть явно подтверждены.

Выберите `qa-orchestrator` и передайте запрос, заменив заполнители:

```text
Выполни QA workflow по AGENTS.md.
Источник требований: Confluence pageId=<PAGE_ID>.
Scope: <ФУНКЦИОНАЛЬНОСТЬ>.
Jira project: <PROJECT_KEY>.
Qase project: <PROJECT_CODE>, target suite: <SUITE_ID>.
Подтверждённый тип и приоритет Jira-задач: <ЗНАЧЕНИЯ>.

Сначала прочитай существующие артефакты и подтверди актуальность источника.
Выполняй этапы последовательно с проверкой Quality Gates.
Создавай только отсутствующие сущности после полного duplicate check.
Существующие сущности не изменяй.
```

Для ревью без внешнего создания явно ограничьте запрос этапом Requirement Review и Gate #1. Требования можно передать непосредственно в сообщении, указав источник и доступные сведения о версии.

Репозиторий уже содержит историю запусков. Не используйте записанные там project keys, page IDs, уточнения или старые `PASS` как автоматически подтверждённые входы нового запуска.

## Повторный запуск и ошибки

- Перед resume оркестратор сверяет идентичность, версию и содержание актуального источника. Если актуальность подтвердить нельзя — `BLOCKED`.
- Новые оценки сохраняются датированными разделами с `run_id`; текущий раздел обозначается явно, история сохраняется.
- Изменение требований требует оценки влияния на существующие задачи и тесты. Новая версия не является основанием создавать их копии.
- Поиск дубликатов должен охватывать все страницы результатов; совпадения проверяются по содержанию через GET.
- Для retryable ошибок чтения, поиска и GET допускается до трёх повторов после исходной попытки. Ошибки авторизации и non-retryable ошибки не повторяются.
- После неопределённого результата создания, например timeout, сначала выполняются поиск и GET. Автоматическое повторное создание запрещено.
- Неподтверждённый результат не получает статус успеха. Ошибки и блокировки сохраняются в артефактах и audit log.

Полные критерии и исключения описаны в [AGENTS.md](AGENTS.md).

## Текущее состояние и проверка

По локальной проверке прогона `20260909-001` от 2026-09-09:

- Исторический прогон создал 4 Jira-задачи и 17 Qase-тестов и записал PASS всех Gates.
- Текущая оценка `20260909-local-review-002` выявила недостатки содержательной проверки: наблюдаемость создания/изменения записей, пробелы по краям пароля, изолированную обязательность полей, доменный regex-кейс и управление тестовыми данными.
- Текущий статус: **Gate #1 BLOCKED**, **Gate #2 BLOCKED (унаследован)**, **Gate #3 BLOCKED**. Исторические PASS сохранены только как история.
- Jira/Qase внешне не изменялись при исправлении артефактов. Перед resume требуется подтвердить актуальность источника и входы по AGENTS.md.

Результаты проверки и исправлений фиксируются в [audit-log.md](artifacts/audit-log.md). Для продолжения нужны подтверждённые решения по блокирующим находкам и повторная содержательная проверка модели.

При первом запуске оркестратор создаёт state и audit, указывает NOT_RUN для Gates и null для ещё отсутствующих активных артефактов. Наличие исторических файлов не делает их активными. Текущая схема не требует pageId для текста пользователя и допускает отсутствующую версию. Для продвижения необходимы подтверждение актуального источника и SHA-256 его текста; при миграции текущая актуальность намеренно оставлена неподтверждённой.

Перед переходом между этапами запускайте `npm --prefix .opencode run validate-workflow`. Команда проверяет текущий run_id, источник и хеш текста, активные разделы артефактов, решения Gates и разрешённый next_stage. PASS этой команды означает структурную согласованность, а не готовность требований или успешное прохождение Gate. Регрессионные проверки: `npm --prefix .opencode run test:workflow`. Формат состояния описан в AGENTS.md.

## Следующие шаги

1. Получить подтверждённые уточнения по блокирующим находкам, сверить актуальность источника и повторно проверить Gate #1; после PASS продолжить пилот в тестовых Jira/Qase-проектах.
2. Проверить повторный запуск и восстановление после таймаутов без дубликатов.
3. После подтверждения блокирующих решений обновить `artifacts/workflow-state.json` и повторно пройти валидатор.
4. Проверять интеграции Jira/Qase/Confluence read-only перед внешними операциями.
5. При проектировании тестовой модели подтвердить подготовку данных, наблюдаемость результатов и достаточность сценариев.
